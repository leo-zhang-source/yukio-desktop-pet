# Mac 聊天历史在系统重启后重复保存：修复与复测

本次只修复[真实助手验收](AGENT-ACCEPTANCE-20261029.md)发现的重复读取问题。未发布新版本，也未替换用户正在使用的桌面 App。Claude 真实账号验收按用户要求跳过；Windows 继续暂缓。

## 原因和改动

在原来的 macOS 虚拟机中再次重启，两个 Codex 聊天文件的系统设备号从 `16777229` 变为 `16777232`，文件编号、大小、创建和修改时间、完整 SHA-256 全部保持不变。旧记录器将“设备号 + 文件编号”作为身份，误判为文件被替换，保存了 56 条相同内容和两条重置事件。

现在对提供有效卷 UUID 的 Mac 文件系统，使用卷 UUID、文件编号与创建时间组成持久标识。通过已打开的文件描述符读取 UUID，避免另查路径的竞争；读取过程中仍验证内容哈希和临时文件身份。实现使用 Apple 的 [`fgetattrlist` / `ATTR_VOL_UUID`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/getattrlist.2)，不启动外部命令，不增加用户配置。

旧版检查点升级时，即使设备号已经变化，也必须同时满足原文件编号和整个已保存内容前缀的哈希一致，才复用读取位置与任务配对状态。新格式仍会识别卷、文件编号或创建时间变化；截断和已有内容改写仍产生重置。无法取得有效 UUID 的文件系统继续采用保守检测，不把不确定的替换当成同一个文件。此前已经产生的历史代次保留，不自动删除或改写旧记录。

代码提交：`fee262991bbbed1e03d4279454dff31ef632c983`、`8877406aaa2d9bdb5cd6d47411fb3eae640942b0`。

## 已取得的结果

- 固定源码的 281 项工作台检查通过，包括 9 项新增检查；覆盖设备号变化后不重读、跨重启继续追加和配对、旧检查点升级、真实替换、截断、内容改写、未写完的一行和无 UUID 时的保守行为。Mac 原生文件 API 检查实际执行。
- 冻结包在宿主 Mac 的隔离人工样例检查通过；去掉 PATH 中的 Python 后仍能运行，源文件清单、重开服务、退出记录器、上下文与聊天历史检查通过。该结果仅作为包检查，不替代独立虚拟机结论。
- 在独立虚拟机安装后，旧检查点从原来的设备号升级到当前设备号，仍为 114 条、两条既有重置事件，没有再次保存旧内容；两个源均获得持久标识。
- 完整重启客体操作系统后，两个源的持久标识、内容哈希和第二代记录保持一致，记录仍为 114 条、重置事件仍为两条，记录器本次新增为 0。此轮设备号本身没有再变化；设备号变化的控制用例与此前实际变化后的旧检查点升级分别记录，不混称为同一次复现。
- 完全关闭客体、结束原虚拟机进程，再用同一系统磁盘重新启动后，设备号实际从 `16777232` 变为 `16777234`，两个文件编号和完整内容哈希未变。修复后的持久标识和第二代记录保持一致；仍为 114 条、两条既有重置事件，本次新增为 0。原来导致重复的实际条件已经再次出现，此次没有重复保存。
- 系统重启和完全关机再启动后，都用安装包运行环境实际调用已登录的 Codex 生成新的英文解释；两次生成前均没有该缓存，结果均为 `mode=model`、`model=Codex`。三段正确解释购物总价、之前的读取说明和用户目的；生成前后均为 114 条记录、两条历史重置事件。

此轮通过实际安装包内的后台服务与本机接口检查历史及真实解释，没有重复进行原生窗口的逐页操作验收。普通用户首次使用指引、正式签名和公证、正式统一发行仍按各自范围继续验收；不能把本次修复结论扩大为整个 App 已可正式分发。
