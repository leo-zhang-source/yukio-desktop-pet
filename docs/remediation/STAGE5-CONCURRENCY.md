第五阶段仍是“小步整理与长期维护”，但每一步都必须考虑并行使用。例如 Codex 的 A、B 聊天与 Claude 的 C、D 聊天同时运行，A 等待回答、B 执行工具、C 出错、D 刚结束，Yukio 应分别记录这些事实；用户查看 B 时，A 的问题仍能找回，回复 A 不能发给 B，C 的失败不能让 D 也显示失败。角色当前只展示其中一项，不等于其他任务没有在工作。

本要求也用于当前的[聊天状态与角色动作修复](ROUND2-STATUS-PLAN-20261031.md)，无需等到阶段 5 才避免串号。它扩展[问题清单 V-03](ISSUES-TO-FIX.md)，不把尚未执行的场景登记为新 bug。

## 如何串入第五阶段

| 原任务 | 加入的并行要求 | 主要风险 |
| --- | --- | --- |
| 5.1 统一设置读取 | 明确哪些设置作用于整个 App，哪些属于来源、聊天或单次解释；共享读取入口不等于所有聊天共享状态 | 改 A 的配置意外改变 B，解释发往旧接收方 |
| 5.2 整理问题卡状态 | 每个问题独立保存草稿、选择、发送状态和回执；绑定来源、聊天、轮次及请求身份 | 切题后旧回执改到新问题，重复发送或误批准 |

| 5.4 有依据地调整后台读取 | 一次调整一条链路，限制每批工作量，保留来源内顺序；跨来源分别推进 | 乱序、重复、停止后继续更新、后台清理误伤其他 Agent |
| 5.5 文档与依赖 | 记录实际支持的客户端、版本、并发规模、身份来源和不支持的场景 | 把顺序测试或单个客户端结果宣称为全部兼容 |
| 5.6 资料归档 | 保留不同来源和聊天的归属与来源记录；备份恢复不覆盖之后新增资料 | 同名文件覆盖、旧记录混进新会话 |
| 5.7 开发记录 | 每次涉及状态、输入、解释或读取的改动，注明验证了哪些并行场景 | 只验单聊天，整理后重新引入串号 |

## 必须保持的行为

- **身份明确。** 不同来源可能出现相同编号，同一聊天有多轮请求；用来源、会话、轮次和具体请求区分。必要时区分运行代次，避免重启或重试复用编号。标题只用于显示，不作为发送对象的凭据。
- **查看与运行分开。** 固定跟随 A 时，B 的新消息不能抢走 A 的输入焦点；自动跟随时先明确优先顺序和并列规则，避免频繁跳动。其他待处理任务应有可达的列表或提示。
- **回答只作用于原请求。** 发送前核对问题仍有效且目标一致；切聊天不改变已经发出请求的归属。重复点击不能造成重复提交；无法确认是否已送达时显示待确认，不能盲目重发。
- **结果与通知分别管理。** 单个工具、子 Agent 或一轮回复结束，不等于父任务或所有聊天完成；查看或放下 A 的通知，只改变 A 对应通知的已读状态。
- **解释范围明确。** 单聊天解释只使用该聊天获准的材料；项目汇总明确列出所含聊天。切换或停用后，迟到的结果不能覆盖当前聊天，也不能继续安排已停止的自动请求。
- **故障相互隔离。** 一个 Agent 未登录、超时、断线或产生无法识别的记录时，其他来源继续可用。停止跟随或退出 Yukio 不应结束用户的 Agent 工作进程。
- **父子关系有依据。** 多个独立 Agent 与同一任务的子 Agent 都纳入范围，但只按客户端提供的可靠关系连接父子任务。关系不可得时分别展示并说明限制，不能凭时间或名称猜测。

## 实际验收矩阵

下表为完整关闭条件。候选 49 已完成部分实际场景：MC-02 的四聊天并发、MC-07 的一次解释切换／停止、MC-08 的单来源记录进程停顿，详见[实际包记录](CANDIDATE49-INDEPENDENT-20261101.md)。其余组合仍待验，不将部分场景通过标为整张矩阵完成。人工样例与独立环境实际客户端证据分别记录。

| 编号 | 操作场景 | 通过条件 |
| --- | --- | --- |
| MC-01 | 同一 Agent 的 A、B 同时运行，A 失败，B 成功；再交换顺序 | 状态、工具结果、结束依据各自正确；同名聊天也不混淆 |
| MC-02 | 至少两种受支持 Agent，各开两个聊天，共四个聊天同时工作 | 能分别看到四项活动，持续收到更新；一项停止或结束不使其余任务停更。记录客户端版本与实际并发数，不把“四个通过”说成无限并发 |
| MC-03 | A、B 同时提问；分别输入不同中文草稿，反复切换，发送时又出现新问题 | 草稿、选项与焦点归属正确；每次有效回答只到对应请求一次；过期问题不能被误批准；切题、关闭重开、失败重试各检查至少 10 次 |
| MC-04 | 同一任务内多个工具或子 Agent 交错运行，一个失败、一个成功、父任务继续 | 子任务事实可分别查看；不因单个子任务结束判定父任务完成；关系缺失时明确显示边界 |
| MC-05 | 延迟回执、重复事件、取消后续跑、App 退出重开和旧事件回放 | 旧回执不修改新请求；同一事件不重复通知或写入；已结束的旧活动不制造“正在工作” |
| MC-06 | 固定跟随 A，同时 B 提问、C 完成；再切自动跟随和手动切聊天 | 不抢走正在编辑的输入；其他问题和通知仍可访问；放下 A 的牌不清除 B、C；选择规则可解释、可重复 |
| MC-07 | A 正在生成解释时切到 B，再停止 A；另测明确授权的项目汇总 | A 的材料或结果不显示成 B 的内容；停止后不再安排 A 的新请求；项目范围与接收方符合预览 |
| MC-08 | 一个 Agent 未登录、断线或大量产生记录，其他来源正常工作 | 单个来源错误不拖垮页面；其他任务继续更新；突发负载下仍能输入、切换和退出 |

MC-02 的首组目标可使用 Codex 与 Claude；Deep Code 按其声明支持的实际能力另记验证，不能借用前两者的结果。真实客户端缺失、账号未配置或无法取得父子关系时保留待验／明确限制，不以模拟数据代替真实通过。

性能先沿 5.3 测量空闲、普通增长、突发增长三类负载，每类至少 3 次，记录数据规模、同时工作数量、界面停顿及各来源更新延迟。根据测量在实现前确定阈值；不能测完后放宽标准。连续使用验收仍需真实交互至少 30 分钟，记录其中并行操作时段，不能以等待时长代替。

## 关闭条件与修复顺序

先把身份、状态和通知规则落实到共同样例，再逐步整理问题卡和读取链路，最后做实际包的并行验收。发现错发回答、误批准、跨聊天污染或资料丢失，相关项不得关闭。每项记录源码、安装包版本与哈希、系统、客户端、并发规模、操作及证据；未验证的客户端和场景继续明确列出。
