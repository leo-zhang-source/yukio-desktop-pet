# 长期维护手册

2026-11-07。共同检查、到期报告、依赖审计、证据校验与人工数据恢复入口已实现。用户随后明确授权定时检查，现已启用 Codex 本地自动任务，详见 [定时检查执行规范](SCHEDULED_CHECKS.md)。每次执行均保存真实结果；本地调度可用性、后续实际触发与通知投递不能由一次配置成功推导。


## 实际命令入口

在当前维护工作树根目录执行；Python 必须 3.12+，Mac 的 UI 检查需要 Swift 6.1+、Node 22+。本机可将 `python3` 换为 `/opt/homebrew/bin/python3.13`。以下每个目录都必须此前不存在，重复执行换一个批次名称。

```sh
MAINT_ROOT="$HOME/.codex/backups/yukio-maintenance-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 -p "$MAINT_ROOT"
python3 scripts/maintenance.py check --out "$MAINT_ROOT/status"
python3 scripts/run-remediation-checks.py --repeat 2 --out "$MAINT_ROOT/checks"
python3 scripts/maintenance.py verify-evidence --evidence "$MAINT_ROOT/checks" --out "$MAINT_ROOT/verified"
python3 scripts/run-source-benchmark.py --out "$MAINT_ROOT/performance"
python3 scripts/maintenance_recovery.py drill --out "$MAINT_ROOT/recovery"
python3 scripts/maintenance_recovery.py archive --source "$MAINT_ROOT/recovery" --out "$MAINT_ROOT/archive"
```

`check` 的退出 0 只表示登记/结构一致，报告中的到期项、未知兼容和暂停验收仍需处理；它不等于产品验收。`verify-evidence` 默认要求当前 HEAD 与工作区指纹，以及完整两遍无跳过原始日志。文档提交后可显式 `--revision <实际测试提交>`，但代码/配置指纹仍必须相同。提供 `--package <ZIP或DMG>` 时读取同目录 build.json，核对同源与包 SHA；`--independent <报告>` 只检查报告绑定/必填字段，人工真实性须另行审查。

依赖审计单独创建维护环境（不放入 App），先核对 Python 3.13 arm64 与工具锁对应，然后：

```sh
python3 -m venv "$MAINT_ROOT/auditor"
"$MAINT_ROOT/auditor/bin/python" -m pip install --require-hashes --only-binary=:all: -r scripts/maintenance-tools-requirements.txt
python3 scripts/maintenance.py dependencies --auditor "$MAINT_ROOT/auditor/bin/pip-audit" --out "$MAINT_ROOT/dependencies"
```

只读查询依赖公告服务，**不执行 `--fix`**。退出 1 的 findings 要逐项分析调用路径；unknown/超时/缺包不能当安全。Pillow 13 的本轮定向升级经过公告审核、像素实验与构建，和自动升级机制无关。CPython、原生库、Sparkle及外部助手需另查官方公告。

Actions 复核使用官方 `gh-actions-lock` v0.4.1。维护者可安装固定版本扩展，再运行 `gh actions-lock .github/workflows/remediation-checks.yml --verify-local`（离线覆盖）和 `--verify`（联网出处）；不手填 actions.lock。更新 action 时先用官方工具生成候选，再评审具体 SHA，并更新政策中的认可哈希和 action 台账。当前工作流候选不会自行上传或运行。

新增/移除测试后，先解释范围，再更新 `maintenance/test-inventory.json`；禁止脚本自动接受新清单以掩盖漏测。依赖/工作流/发行配置的认可 SHA 同样只能在完成复核后更新。周/月/季任务完成时填 `last_reviewed` 和实际证据路径，不能把运行状态报告本身当作上游复核已完成。

失败日志留在原目录；修复后用新目录复测。遇到输出存在、零测试、意外跳过、源变化或日志不完整，先定位，不改门槛绕过。大文件按 [资料地图](STORAGE.md) 放 NAS 并做回读。

## 责任与授权

- 维护执行者：当前承担开发任务的人或 AI，负责审查起点、复现、实现、验证、归档与更新证据。每张真实任务卡记录实际执行者和日期。
- 产品负责人：用户，审查重大架构、不可逆/删除、付费、暂停验收恢复和当次远端上传范围。普通已授权步骤连续推进，不逐步索取确认。
- 质量复核者：对改动做批判性复核；若是同一执行者必须明确为自审。需要独立结论时记录真正的第二位评审或独立环境，不能换个身份代写通过。
- 用户配置与数据归用户。维护者不得复制作者凭据给测试机，公开诊断不得包含正文、令牌、完整私人路径或真实会话 ID。

## 一套记录足够

继续使用 [任务卡](../TASK-TEMPLATE.md)，保留问题、范围、验收、结果、回退五个核心字段。增加来源/包/客户端/并发规模只是相关任务所需信息。不要再手写一套重复的逐项通过表：机器摘要来源于实际结果，ROADMAP 只链接摘要和未完成项。

已建立的一份维护登记（`maintenance/policy.json` 及同目录清单）包括当前产品线、受保护资源、依赖复核时间、客户端矩阵和开放问题；工具生成可读摘要。拟定状态：`passed`、`failed`、`not_run`、`blocked`、`paused_by_user`、`deferred_by_user`。没有证据时不能默认为 passed；“不在本次范围”必须说明原因。

每份证据只创建新目录，记录源码提交及工作区指纹、测试命令/工具/系统、摘要与原始日志 SHA。有包时记录 DMG/ZIP SHA 与 build manifest；有独立流程时记录隔离条件/初始依赖/账号来源/真实操作。私有原始日志留私有区；仓库只保存合成证据或脱敏摘要。所有后续修改使相关旧通过失效，重新验证受影响范围。

## 依赖升级流程

1. 记录当前/候选版本、发布日期、官方修复/风险、运行或构建分类、是否影响最低系统与许可证。不采用“全升最新”。
2. 使用新的候选目录更新固定版本与可信来源哈希；核对 Swift revision、Python 归档及所有 wheel。更新维护工具自身也按此流程。
3. 执行适用回归与同提交完整构建，核验实际包内依赖。Sparkle 变化额外验证旧包升级、取消、损坏包、Unicode/含空格安装路径和重启后的真实运行版本。
4. 有风险公告时核查确切包/版本/平台与调用路径。扫描器说“未知/跳过”不能记“无漏洞”。例外必须有原因、负责人、复核期限和退出条件，不永久白名单。
5. 本地验证、候选包、独立验收、远端上传分开记录。没有上传授权不推送/开 PR/启用 bot；无法完成的项目报告真实限制。

## 故障分级与处置目标

以下是活跃维护期间的响应目标，不是全天在线服务承诺；严重性基于实际影响，不能仅按上游版本号判断。

| 级别 | 触发例子 | 处置与关闭 |
| --- | --- | --- |
| P0 | 已证实数据损坏、凭据泄露、错发回答/误批准 | 发现即停止相关测试/候选交付、保留证据与新增资料，立即向用户报告；远端撤回/数据恢复按明确授权；根因修复、邻近场景复验、复盘后关闭 |
| P1 | 当前支持流程崩溃、系统性卡顿、测试失败、来源/包错配 | 当前维护会话优先定位，最迟下一次候选前处置；未修不得写该项通过。需要外部环境则明确阻塞 |
| P2 | 非核心兼容、文档漂移、常规依赖升级、可恢复的小问题 | 纳入下一维护批次并记录复核点；不为完成数量顺手大改 |

失败复盘写触发、影响范围、首次证据、根因、最小修复、预防回归和未覆盖项。不能用增加全局状态、放宽测试阈值或反复重跑掩盖原因。

## 备份、归档和恢复

| 资料 | 存放与保留方式 |
| --- | --- |
| 正式输入/源码 | Git 及清晰来源索引；已验收动画输入优先；不作为“可重建缓存”删除 |
| 构建包与大型长期证据 | 维护环境按任务存 `nas:/volume1/leo/yukio/maintenance/<任务标识>/`，这是归档根目录；每次执行前检查连接、写入和容量，校验后记录真实最终路径 |
| 可重建生成物 | 标明生成命令与输入哈希，先确定无源文件后再拟定忽略规则；没有释放空间授权不移除原件 |
| 用户数据库/配置 | 私有目录，一致性快照与权限保护；不上传 GitHub，不混入公共证据或安装包 |
| 密钥/助手登录 | 使用者各自保管；不拷贝进源码/安装包/项目归档，NAS SSH 私钥只在本机 |

NAS 只用于维护数据，不是产品运行条件。SSH 使用别名 `nas` 或规定的 1529 端口，实际根目录 `/volume1/leo`。传输后验证大小与 SHA，App/源码包另核对符号链接和执行权限；再从 NAS 回读到新目录核验，不能把上传成功当恢复成功。失败保留原件与日志。

数据库先用人工记录验证一致性快照、`integrity_check`、模式版本、来源保存点及逐条记录。快照后追加新记录，再验证 App 回退/恢复流程不会把它们覆盖。实际用户库操作需当次明确范围；默认不执行恢复、不删除旧副本。无效/未知 schema 要明确拒绝，不自动重建库。

工作目录状态仅标“使用中/保留/待核实/拟退役”，本阶段不自动删除任何工作树。恢复点应包括必要未跟踪/被忽略文件的分类清单，不能以 Git 提交假定所有资料都已保存。

## 维护是否真的在起作用

按最近几次真实任务检查：发现失败到定位的耗时、首次失败保留率、未批准跳过数、测试发现遗漏数、证据错配拒绝数、依赖复核逾期数、恢复演练通过/失败、支持矩阵未知项。初始要求为错发/丢失 0、未知如实报告、未批准跳过 0、每个通过均有本次来源；不以代码行数或通过项总数替代质量。

先用一项真实小修复试运行，发现维护流程重复就简化。长期维护的交付是可执行机制、真实演练和清楚交接；它不意味着未来永远无需修复。

## 本维护环境的 NAS 复核

先用 SSH 别名 `nas` 核实 `/volume1/leo` 可达、可写及容量。NAS 当前未开放 SFTP；本轮首次 scp 默认协议失败，失败日志保留。维护入口使用 SSH 流传输，无需启用服务或改 NAS 配置，仍沿用已配置的 1529 端口。

```sh
python3 scripts/maintenance_recovery.py nas --source "$MAINT_ROOT/archive" --host nas --remote-directory /volume1/leo/yukio/maintenance/一个此前不存在的目录 --out "$MAINT_ROOT/nas-readback"
```

远端父目录需已存在且可写；新目录已存在会拒绝，传输失败保留本地原件。入口比较远端/回读 SHA，解包到新的本地目录并核对清单。没有删除或原位置恢复操作。其他维护者使用自己的 SSH 别名和明确目录，NAS 不成为产品运行条件。
