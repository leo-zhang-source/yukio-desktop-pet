## 执行频率

2026-11-08 按用户要求改为每 **60 小时（两天半）**触发一次，每次进行轻量检查并核对其他周期的到期状态；原每天 09:00 的设置已被替换。7/30/90 天复核按最后一次**有完整证据的成功执行**计算，到期后在下一次触发时执行；中断后不伪造漏跑日期，也不一次重放所有历史次数。显示时间沿用 America/Los_Angeles，具体触发时刻由 Codex 调度器安排。

| 周期 | 实际检查 |
| --- | --- |
| 每 60 小时 | 当前维护入口、分支/工作区状态、工具可用性、维护登记/锁/测试清单/文档链接、近期失败及证据是否仍适用、本地容量；保留未完成与暂停项的原状态 |
| 每 7 天 | 固定 Python 构建依赖的只读公告审计；失败与范围复核；NAS 可达、目录可写、容量与已登记归档哈希的只读检查 |
| 每 30 天 | 官方依赖/运行时/助手客户端变更与安全公告复核；Mac 完整回归两遍及证据校验；读取性能基准；官方 Actions 锁核验。新版本只记候选与影响，不执行升级 |
| 每 90 天 | 人工 SQLite 恢复与文件归档演练；从已登记 NAS 归档回读到新目录核对哈希和清单，并验证原件仍在。不得恢复覆盖用户实际数据库 |

初始周期依据 2026-11-07 的真实实施证据。轻量检查不重复运行未到期的完整回归；源码/工具环境变化使旧证据不适用时，记录具体差异并按范围安排检查。在未提交开发改动或其他任务占用同一构建目录时，先完成不冲突的只读项目，留下未执行原因，不改分支、不重置工作区、不把未执行当通过。

运行记录存入 `~/.codex/backups/yukio-maintenance-scheduled/runs/<日期时间-唯一标识>/`；可写范围限于这些证据、测试所需的已有构建缓存，以及演练时明确新建的 NAS 维护目录。共享周期状态为该根目录下的 `state.json`。每次保留 start/summary、必要原始日志、退出码、来源指纹和实际工具版本；失败原样保留，重试使用新目录。

`state.json` 保存每个周期最后尝试时间、最后成功时间、证据路径、证据哈希及问题基线。使用排他锁避免重入；成功写到新临时文件后原子替换。只有本周期所需项目均真实完成才前移成功时间；失败、超时、工具缺失和未执行不前移。手工完成且证据完整的检查可以纳入周期，不凭日期或历史通过文字认可。

为保留历史记录，轻量检查仍使用 `cycles.daily` 键名，但周期改为 `interval_hours: 60`；读取带时区的 `last_success_at`，以实际经过 60 小时计算 `next_due_at`，不再使用旧的 `interval_days: 1` 或日期级 `next_due`。`last_success` 日期仅作历史显示。每次调度触发均执行轻量检查，`next_due_at` 是维护记录的参考时间，不是调度器承诺的触发时刻，也不用于跳过已触发的轻量检查。其他三个周期继续使用原 `interval_days`、`last_success` 和 `next_due`。

仓库 `maintenance/policy.json` 保留经人工审查的基准日期，自动任务不改动它或依赖锁。周期判断综合该基准与可验证的独立运行状态；在摘要中区分“登记基准已到期”和“已由本次自动检查覆盖”，不得把一次 `check` 的退出 0 当成月度研究或季度恢复完成。

## 结果判定

- `passed`：本次应执行项目均有完整有效证据，无新增异常。
- `failed`：结构/锁/清单错误、测试失败或意外跳过、证据错配、审计发现适用风险、超时/联网失败导致未知、工具缺失、到期检查未能完成、NAS 不可达或归档损坏。明确失败项、影响、证据位置和建议的下一步；禁止通过自动修复掩盖结果。
- 已登记的独立验收暂停、Windows/云端暂缓、未上传、未公证与待人工验收等保留为背景限制。状态与影响没有变化时，不把它们当作新发现；发生实质变化时重新评估。
- 新版本发布本身不是故障。月度研究记录官方链接、发布日期、适用版本和已验证/推断/未知；依赖审计不代表全部原生库或运行时均安全。

无论结果如何，都不自动修改产品源码、资源、依赖版本、锁文件或现用 App，不自动提交、推送、开 PR、发布、上传 GitHub 或触发远端工作流，不恢复暂停验收、不删除资料、不付费。需要这些动作时只留下具体建议，等待另行授权。
