## 怎么使用这份清单

- **P1：先处理。** 影响核心使用、用户对资料去向的判断，或阻碍正式安装和更新。标为“待定位”的条目先复现，再决定改哪里。
- **P2：随后处理。** 已有替代操作，但会让新手卡住、误操作或无法理解结果。
- **P3：整理与一致性。** 不应抢在核心问题之前大改。
- **已确认**表示在注明版本和条件下有证据；**待定位／待确认**不等于已经找到代码错误；**发布条件**需要账号、发布渠道或实际环境，不能靠改几行代码替代。

## YK-01：解释预览写错资料接收方

**现象与影响：** 工作台已选择 Codex，历史详情仍写“使用你设置的千问”；发送预览写“发送到你设置的内网千问”，并声称内网服务器处理、接口没有鉴权。这会使用户误解资料去了哪里，以及使用谁的账号。10 月 30 日在自动选择下发现，31 日在明确选择 Codex 的独立环境中再次确认。

- **复现：** 不配置内网模型，选择 Codex → 进入记录详情 → 点击解释 → 查看发送前的预览。本次旧预览测试停在取消，没有据此向错误声明的目的地发送。
- **从哪里处理：** [explanation.js](../../tools/activity-workbench/dist/explanation.js) 中的状态、接收方和鉴权说明写死为旧文案。让配置、预览、实际发送使用同一个已解析的接收方信息，中英文一起修。
- **改动风险：** 只把“千问”改为“Codex”仍会在自动选择、Claude 或自选服务下出错；预览后切换配置也可能造成文案与发送不同步。
- **验收：** 自动、Codex、Claude、自选内网模型、未配置和未登录逐项检查。用户在确认前能看懂接收方、摘录范围和账号用量；发送时仍是预览中的选择，变化后要求重新预览；取消不发送。

## YK-02：命令成功了，工作台却没把成功回执对应到那一步

**现象与影响：** 本轮真实测试只执行一次打印命令，官方客户端记录明确包含输出和成功退出码。Yukio 历史也保存了这个成功回执，但工作台结果仍是“一次工具操作；结果仍不明确”。生成的解读因此缺少实际成功的依据。它没有把失败说成成功，也没有丢掉原始成功回执；问题在于能够呈现的信息不足。

- **复现：** 使用 Codex 0.165.0，在专用空测试目录请求只执行一次 `/bin/echo YUKIO_STAGE4_ACTIVITY_20261031`；选择该聊天，对照客户端结果、Yukio 历史和工作台结果说明。本轮样本只有一次，不代表所有 Codex 操作都有此现象。
- **已定位的环节：** 外层 `exec` 请求在事件 130；内层 `CommandExecution` 成功回执在事件 132，已保存 `exit_code=0`、`outcome=succeeded`，但标为 `association=unlinked`、不能归到外层步骤；外层回执在事件 133，仍为 `unknown`。见 [codex_results.py](../../tools/activity-workbench/core/yukio/codex_results.py)、[context_view.py](../../tools/activity-workbench/context_view.py)、[glance_view.py](../../tools/activity-workbench/glance_view.py)。这些事件号只适用于本轮保留样本。
- **修复方向与风险：** 先研究客户端有没有明确的父子关联字段，再支持这种嵌套命令。如果确实缺关联，至少能单独展示“这一命令已成功，但尚不能归到某个外层步骤”。**不能按时间相邻或最近一次调用强行配对**，否则可能重新引入 A、B 聊天串号。
- **验收：** 单命令成功、失败、取消，以及两个交错命令分别核对。成功回执可见且归属有依据；没有依据的关联仍保持待确认。重开、重复记录和旧格式样本也要检查，既有结果归属检查继续通过。

## YK-03：问题卡偶尔无法输入，原问题仍未定位

**现象与影响：** 用户报告有时能输入、有时不能；这会阻断回答。此前诊断窗口当次可正常输入，完整候选在本机的拼音选词、切到 Finder 再回来、活动刷新时继续选词三种操作也成功，但这些成功不能排除偶发故障。

- **下一步先做什么：** 在实际问题卡记录触发前的操作：点了哪个窗口、使用何种输入法、是否切聊天、是否正在发送、是否刚收到新活动。复现从别的 App 点击输入框、中文选词、刷新、隐藏重开和切聊天；记录焦点、可编辑状态、草稿长度及请求编号，不保存私人回答正文。
- **入口：** [QuestionPanel.swift](../../YukioPlayer/Sources/YukioPlayer/QuestionPanel.swift)、[问题输入诊断说明](../../tests/remediation/native-input-probe/README.md)。此前已修复的是“发送失败后草稿丢失”，不是已经证明修好了所有不能输入。
- **改动风险：** 为抢回焦点而不断激活窗口，会打断用户在别的 App 输入；每次刷新重建文本框也可能破坏中文选词和草稿。
- **验收：** 先保留稳定复现和修复前失败证据，再验证上述组合；真实测试聊天能收到一次且仅一次正确回答，失败时草稿保留，切换聊天不误发。独立 Mac 的真实问题卡链路仍待完成；搜索框能打字不能替代它。

## YK-04：公开更新地址当前不可用

**现象与影响：** 候选包内的[公开更新列表](https://github.com/leozhang8654/yukio-desktop-pet/releases/latest/download/appcast.xml)在 2026-10-31 22:07 UTC（洛杉矶 15:07）实际请求返回 HTTP 404。App 无法从这里获知可用更新。这能解释当前更新失败的一条直接路径，不能解释所有历史失败。

- **处理方向：** 先恢复公开发布渠道，再统一准备更新列表、签名、下载包和说明；确认普通访客无需开发者登录也能访问。此前报告记过账号暂停，**本轮没有重查账号状态**，不要把它写成今天重新确认的原因。
- **入口：** [SoftwareUpdates.swift](../../YukioPlayer/Sources/YukioPlayer/SoftwareUpdates.swift)、[更新说明](../UPDATES.md)、[阶段 4 构建与交付记录](STAGE4-DELIVERY.md)。本机临时更新源已通过的升级，不代表公开源恢复。
- **改动风险：** 更新列表指错包、版本号倒退、签名不匹配，会导致无法升级或安装错误版本；不能临时关闭签名检查来获得“成功”。
- **验收：** 从普通网络读取公开列表并下载实际包，核对哈希、版本与来源；独立 Mac 从真实旧版本完成升级、重启、读取原设置和资料。服务不可达、坏包和取消时旧 App 仍可用。按阶段集中发布，不逐条修复就发一版。

## YK-05：正式下载后的首次打开还没有通过

**现象与影响：** 当前候选使用临时签名，系统的单独来源检查仍拒绝。VM 中传入的文件没有普通浏览器下载常见的隔离标记，所以这次能打开不能代表普通用户下载后也能顺利打开。用户目前没有 Apple Developer 开发者账号，这是已知发布前置条件。

- **处理方向：** 先保留候选继续功能测试；准备正式公开交付时，完成正式签名、公证和实际下载验收。不要把“关闭系统保护”写成产品安装步骤。
- **入口：** [完整 Mac 构建说明](MAC-BUILD.md)、[阶段 4 交付记录](STAGE4-DELIVERY.md)。这项不是工作台代码修复能够单独解决的。
- **改动风险：** 换签名身份或重新封包后，旧哈希和旧安装结论不能直接沿用；正式包必须重新核对。
- **验收：** 在没有开发信任例外的新 Mac 环境，用普通浏览器下载最终包，保留系统保护和下载标记，按公开说明安装、首次打开和配置；记录实际系统提示、包哈希和版本。

<a id="yk-06"></a>
## YK-06：缺助手、缺登录时，页面没有把下一步讲清楚

**现象与影响：** 选择 Claude、Deep Code 后，历史页能说明没有来源目录，却缺少就近的安装、登录、配置和产生第一条记录的指引。新手看见空白记录，难以区分“尚未用过”“没装好”“没登录”和“连接故障”。本轮明确选 Claude 还出现了“可用性检查超时”；之后直接检查客户端，约 1 秒返回未登录。两次检查条件不同，不能认定超时一定是错误判断。

- **复现与处理：** 在未安装、已安装但未登录、已登录但无记录三种环境分别打开页面；为每种状态提供可执行的下一步和官方安装／登录入口。Claude 超时另记每个检查阶段的耗时与失败原因，区分冷启动、兼容性检查和登录检查。
- **入口：** [agent_explanation.py](../../tools/activity-workbench/agent_explanation.py)、[Agent 解释说明](../AGENT-EXPLANATIONS.md)、历史页面与空状态文案。菜单已有后台回答设置入口，问题是当前失败处缺少解释来源和记录来源的就近指引，不应写成“整个 App 没有任何设置”。
- **改动风险：** “找到可执行文件”不等于“已经登录可用”；自动切换来源会改变接收方。不能静默使用作者的账号或把未登录显示成成功。
- **验收：** 一个没有开发经验的测试用户仅按页面和公开说明能完成安装、自己的登录与首次记录；缺少可选助手时，已有历史和其他独立功能仍能使用。明确选择 Claude 时，失败不能伪装为 Claude 已成功。

## YK-07：首页解释曾被状态检查拦下

**现象与影响：** 本轮第一次首页解释提示“这次说明把已结束的工作说成正在进行，先保留本机情况”；同一测试聊天的整体解读随后成功，切回 Codex 后另一次首页解释也成功。因此这是已发生的单次失败，不能写成“解释功能完全不可用”，也不能用第二次成功掩盖第一次。

- **下一步：** 在专用无私人资料的样本中保存送入模型的事实、模型原始输出和校验理由，复测刚结束、已结束一段时间、仍在运行三种状态。本轮没有保存第一次被拒绝的原始输出，尚不能区分模型写错和规则误判。
- **入口：** [explanation.py](../../tools/activity-workbench/explanation.py) 的 `closed_turn_claim` 校验，以及生成当前说明的输入整理。
- **改动风险：** 直接删掉校验会让过时或错误的“仍在工作”说明显示给用户；无上限重试会消耗账号额度。
- **验收：** 已结束的任务不被描述为仍在执行；确实错误的模型结果仍会被拦下；失败时保留本机事实、说明如何重试，并限制重复调用。保存成功和失败样本，不只挑成功截图。

## YK-10：按 Escape 会清空正在编辑的回答

**现象与影响：** 问题卡有文字时按 Escape，当前实现直接清空；为空时再按才收起卡片。该行为在本机完整候选中已看到，源码也明确如此。它可能让习惯用 Escape 退出选词或关闭窗口的用户丢掉草稿，但目前还没有确定这是不符合预期的产品规则。

- **处理方向：** 先明确 Escape 在“输入法正在选词”“普通草稿”“空输入框”三种状态分别做什么，再改；建议取消输入法选词时不触碰已提交文字，收起卡片时保留草稿，把清空放到明确操作。
- **入口：** [QuestionPanel.swift](../../YukioPlayer/Sources/YukioPlayer/QuestionPanel.swift) 的 `cancelOperation`。
- **改动风险：** 改按键优先级可能影响输入法取消、关闭窗口和发送状态，不能把一类键盘习惯强加到所有状态。
- **验收：** 用真实中文输入法选词和英文草稿分别操作 Escape；结果符合确定后的规则，恢复卡片后文字仍在，不会触发发送、批准或误清其他聊天草稿。

## YK-15：已看到对应聊天，完成牌没有自动放下

**用户报告（2026-10-31）：** 屏幕上已显示某条聊天，或用户手动切到该聊天页面时，Yukio 尚未可靠地放下这条聊天的完成牌。该项可先按已有功能缺陷修复；若现有客户端无法可靠识别聊天身份，再拆为明确支持范围的功能任务。

- **处理方向：** 检查现有 `openChatSession`／`visibleChatSessions`、聊天身份映射与 `acknowledgeVisibleCompletions()`，补齐“确认看到该条通知”的处理。放牌只确认对应聊天的这次通知，不修改任务事实、不清空历史；后续新一轮完成应能再次提示。
- **识别边界：** 只有前台 App 名称、聊天标题相同、刚点击跳转或后台标签存在，都不足以确认看到了对应聊天。优先使用可靠聊天 ID 和实际可见状态；权限缺失或识别不确定时保留手动放牌。无需为此默认采集屏幕正文。
- **验收：** 已在屏幕上、手动切入、点击牌子跳转、多窗口／多屏、遮挡／最小化、同名 A／B 聊天、快速切换分别检查。看到 A 不能消除 B 的通知；等待批准／回答不得被自动确认。
