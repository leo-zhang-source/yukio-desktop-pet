# 阶段 3：关键故障修复与本机验证

2026-10-29。本阶段只推进 Mac，Windows 按用户决定暂缓。阶段 2 先建立可重复的检查，阶段 3 用这些检查修复已确认的问题，再用真实原生窗口检查输入、连接和退出。这里记录的是本地开发成果；正式安装包、独立用户安装与更新链路仍须在阶段 4 验收。

**结论：三项修复已实现并通过本机验证；完整 G3 仍未关闭。** 原用户环境的偶发不能输入尚未确定根因，真实中文输入法选词尚未完成验收。本轮不替换正在使用的 App，不发布安装包，不向 GitHub 推送，不迁移或清空用户历史。受保护的 217 份素材、已验收动画输入和 Windows 专属源码保持原样。

## 改了什么，为什么这样改

### 3.1 让执行结果对应到正确的任务

原来的 Mac 解析器把“刚才有一次失败”暂存在一个共用标记中。A、B 两次调用交错返回时，A 的失败可能被算到 B 上。本轮改为按会话、轮次、调用编号关联；没有足够证据就保留“未知”，不再按到达顺序猜测。迟到、重复、取消、矛盾回执和不同会话分别处理，“操作结束”也不再被当成“已经成功”的证据。

这是内存中的有限状态，不增加用户历史数据库迁移。每个解析器最多跟踪 4,096 个调用；结果仅保留状态与身份等元数据，不保存工具参数或回答正文。原有子助手身份、父会话关系、异步问题确认和完成举牌规则继续保留。

阶段 2 的 13 组公共样例继续使用原有预期事件；同时增加 Mac 与工作台 Python 的结果事实比对，共 230 个断言通过。原来登记的 11 个已知失败已消失，原登记内容保存在 [已解决的阶段 2 缺陷](../../tests/remediation/resolved-stage2-issues.json)。另外仍故意放入错误预期和过时豁免，确认检查会报警，而不是靠放宽规则获得通过。

主要入口：[结果跟踪](../../YukioPlayer/Sources/YukioCore/CodexToolResults.swift)、[Mac 解析器](../../YukioPlayer/Sources/YukioCore/CodexParsers.swift)。修复提交 `1b175108`。

### 3.2 让工作台取得自己的连接地址

原生 App 过去依赖固定端口，旧版本或其他程序占用时容易连不上或连错服务。现在启动时由系统直接分配一个可用的本机端口，服务以专门的就绪消息告知 App 地址，App 只允许访问这次启动的本机地址；日志里碰巧出现的网址不能冒充启动成功。

启动默认最多等待 15 秒，失败会显示对应状态，并提供重新连接和不含私人路径、凭据、聊天内容的诊断信息。重新连接后保留所选页面，但把页面地址换到新服务。工作台出错时设置入口仍可用。单独运行源码启动器时仍保留原端口选项，与 App 自动选择端口的方式分别验证。

历史候选 `fb539825`、`f739ccdd`、`ad4bc936` 经逐文件审查后接入，保留当前 Agent 配置入口；没有用旧目录整体覆盖新功能。检查涵盖空闲端口、同版本同资料服务、不同版本或资料服务，以及无关程序占用四种情况。没有通过强制结束无关程序来释放端口。

主要入口：[原生启动管理](../../YukioPlayer/Sources/YukioPlayer/WorkbenchRuntime.swift)、[窗口与导航](../../YukioPlayer/Sources/YukioPlayer/WorkbenchPanel.swift)、[启动器](../../tools/activity-workbench/launcher.py)。修复提交 `d321c406`。

### 3.3 明确谁负责关闭后台服务

工作台窗口可以反复开关；App 负责它启动的服务，服务负责它启动的三个记录器。关闭窗口时，记录工作可以继续；退出 App 时，自己启动的服务和记录器必须结束。已由其他进程持有的记录器继续运行，不能被这一轮关闭操作误伤。

为覆盖 App 被强制结束、来不及运行退出代码的情况，App 与服务之间持有一条系统管道。App 消失时管道关闭，服务据此收尾自己的子进程。这不依赖进程名搜索或批量终止。检查包含十次重连后历史文件不变、已有外部记录器继续健康，以及强制结束测试宿主后自己启动的进程退出。

真实原生窗口另外做了两组各十次打开／关闭：一组正常退出，一组强制结束测试 App；网页、接口、设置返回、单一服务地址以及三个记录器的退出状态均有记录。接入同期工作台修改后又重做这两组检查。这里使用编译后的原生窗口和源码启动的 Python 服务，是本机集成验证；没有把它称为正式安装包验证。

### 3.4、3.5 先复现输入故障，再只修已证实的原因

使用实际问题卡代码构建独立诊断窗口，输入人工样例，记录窗口焦点、可编辑状态、字符数量和是否匹配样例，不保存回答正文。用户试用后的反馈为“我试了，可以正常输入”。这说明当次试用正常，不能推导为偶发问题已经消失。

检查中另外找到了可以稳定复现的问题：正在编辑的草稿在进入“发送中”时丢失，发送失败后输入框恢复可用，草稿却为空。原因是原生文本编辑器在禁用输入框时丢弃尚未提交的编辑内容。本轮在切换可用状态前取回草稿并保留，不增加自动抢焦点的行为。

修复前，实际窗口复现两次，新增的 AppKit 检查也失败；修复后，该检查连续十次通过。实际诊断窗口完成 30 个输入回合：英文键入加中文粘贴、整段粘贴、刷新、隐藏重开各五次，发送失败后继续编辑十次。每个完成回合只有一条匹配样例的接收记录；十次失败序列均保住草稿。

必须同时保留一条异常：第 7 回合第一次自动粘贴未进入输入框，日志显示问题窗口当时不是活动窗口；重新点击后成功。自动操作时机与 App 焦点问题尚未区分，因此结果是“30 个回合完成，另有一次初次粘贴失败后重试”，不能写成“30 次首次操作全部通过”。中文粘贴也不等于真实输入法选词通过。原用户环境的“偶尔完全不能输入”仍保留根因未知。

主要入口：[草稿保留](../../YukioPlayer/Sources/YukioPlayer/QuestionPanel.swift)、[原生回归检查](../../YukioPlayer/Tests/YukioPlayerTests/QuestionDraftTests.swift)、[输入诊断操作说明](../../tests/remediation/native-input-probe/README.md)。修复提交 `a32b3b0d`。诊断中的发送失败由本地模拟，实际回答通道另有隔离接收端检查；没有向真实聊天发送测试答案。

## 验证版本与范围

最初的开发入口在检查期间仍有其他修改，源码指纹发生变化，因此那轮不能作为稳定验收。随后在阶段 2 检查点 `19bf92e8` 上建立隔离分支 `codex/remediation-stability`，完成上述修复。开发入口同期已提交的工作理解与重启历史修复（截至 `8877406a`）再合入候选，保留其来源与原验收记录。

| 验证版本 | 重复次数 | Swift | 工作台 Python | 网页 Node | 公共样例断言 |
| --- | --- | --- | --- | --- | --- |

两组检查每轮均无失败、无跳过，源码指纹在运行期间不变；两种故意制造错误的检查都能拒绝错误结果。集成版本每轮共 574 项自动检查，230 个公共断言单独计数，不把不同口径相加夸大为功能数量。环境为本机 Apple Silicon Mac、macOS 27.0.1、Swift 6.1.2、Python 3.13.2、Node 25.8.0。

AppKit 检查共享主线程。曾经并行运行时，其他窗口测试阻塞主线程，导致 0.3 秒超时检查直到约 26 秒后才响应。检查入口改为顺序运行，保留原先小于 3 秒的断言，没有放宽超时标准。重复方法见 [检查说明](../../tests/remediation/README.md)，统一入口为 `scripts/run-remediation-checks.py`。

最终集成测试的源码指纹为 `eb2a1b47f8cbf1ac6ffc4d9bdab5ca0d3f55a136cc51dff35d781c432c4e3737`。本记录后续的纯文档补充不改变该测试范围的源码指纹。本轮证据保存修复前失败、修复后日志、原生状态、输入异常和各次源码标识，不用后一次成功抹掉先前失败。

## 尚未完成的验收与下一步

1. 在原用户环境中明确偶发不能输入的触发条件，并完成真实中文输入法选词、切换聊天等实际使用场景；保留现有草稿与状态诊断，不扩大猜测性修复。
2. 阶段 4 从同一源码整理正式 Mac 构建与安装包，验证更新、失败回退以及原资料保留；本阶段没有修复或验收软件更新链路。
3. 用实际准备分发的包，在另一台 Mac 或干净虚拟机中按公开说明完成安装、首次启动、权限、用户自己的账号配置和功能操作。测试目录隔离、模拟服务与本机自动检查均不能替代这项验收。
4. 同期任务已有的其他版本虚拟机记录只对其记录的版本与流程负责，不能借来证明本轮新修复的包已经通过。Windows 保留资料，待用户明确恢复后再安排。

因此本轮可以记录“本地修复与上述检查完成”，不能记录“完整 G3 通过”“所有功能已通用化”或“已发布新版”。

## 保存与回退原则

源码按结果关联、启动生命周期、草稿保留分别留有本地提交，统一开发入口继续使用 `codex/remediation-baseline`。原入口中同时发生的未提交说明保留原样并另存快照，不混入本轮提交。备份索引记录最终提交、证据哈希、NAS 路径以及实际解包恢复结果；恢复到新目录核对后再决定采用，不覆盖后续新增资料。

如需撤回某项修复，先保存当前工作区，再逐项反向提交相应改动，并运行受影响检查；不要直接重置整个开发目录，也不要恢复旧数据库覆盖新历史。由于本轮没有替换安装 App，源码回退不要求改动正在使用的 App。增量 Git 备份依赖已验证的阶段 2、1、0 历史，不能把单独的增量包当成完整仓库。
