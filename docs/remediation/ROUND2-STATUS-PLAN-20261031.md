## 先确定用户能看到的规则

| 观察到的事实 | 建议显示及动作 | 必须保留的边界 |
| --- | --- | --- |
| 正在处理请求、思考或执行工具 | 显示正在工作及当前动作 | 需要当前聊天的实时依据，旧记录不触发 |
| 需要回答、批准或补充资料 | 显示等待用户及对应入口 | 看到聊天不等于回答或批准 |
| 本轮回复结束，但整体目标没有完成依据 | 使用“本轮回复已结束”等中性提示 | 不举表示整个任务完成的牌；不假装仍在运行 |
| 出错、用户中止、断线或观测失效 | 分别显示失败、已停止或状态未知 | 超时不自动判定成功；记录原因 |
| 有明确的任务完成依据 | 可发完成通知，并注明依据来源 | 助手自述与可验证结果分开；不凭结束事件或单个工具成功推断 |
| 对应聊天实际可见、身份可靠 | 确认该聊天当前完成通知并放牌 | 仅改变通知是否已看，不改历史任务结果；新一轮完成可再次提醒 |

完成依据如何从各客户端取得，需要结合实际样本落实；在证据不足时采取中性结束状态，而不是靠关键词或一次模型判断强行补齐。先沿用现有完成通知能力，核对哪些已有触发条件符合此规则，再作最小必要调整。

## 实施顺序

1. **留存失败场景。** 核对用户实际使用的 Yukio、Claude 客户端和版本（桌面／Code／浏览器等）、跟随设置与必要权限。用专用测试聊天复现三项，记录时间、匿名会话代号、事件类型和状态，不记录私人正文。独立环境 Claude 当前未登录，真实 Claude 端到端验收需要测试用户自行完成登录；不能借用作者凭据。
2. **对齐输入与身份。** 同时观察转录／hook、原生活动路由、历史记录与工作台结果，查明“内容有但状态无”丢在哪一段。保留来源、事件时间、会话及轮次关联；重复和乱序事件不得制造完成或工作状态。
3. **修状态含义。** 明确区分执行生命周期、任务完成依据和通知是否已看，在现有数据模型上作必要调整。统一原生角色、工作台与解释输入，先修 YK-14／16；不以新增一个计时器或前端文案掩盖上游缺失。
4. **修可见聊天确认。** 排查已有 `BrowserOpenChat`、Claude 会话映射及 `ActivityRouter` 的可见确认链路。先处理可靠身份可获得的范围；不能可靠识别的客户端另列功能范围及降级行为，不根据同名标题匹配，不因打开 App 清掉所有聊天的通知。
5. **构建并验收。** 固定源码生成新的 Mac 候选，记录版本与哈希，从实际安装包在独立环境复测。每项分别写清通过与未覆盖；本地集中整理后再按阶段交付，不逐小项推送发布。

## 验收矩阵

- Claude：完整任务完成、仅子步骤完成、等待回答／批准、主动停止、失败／断线、恢复续跑、长时间工具执行、无工具回复。
- 多聊天：Claude A／B 同时工作、同名聊天、与 Codex 交错；任何事件、通知与放牌只能作用于真实对应的聊天和轮次。
- 可见性：结束时对应聊天已经可见、手动切入、点牌跳转、多屏其他窗口可见、遮挡／最小化、快速切换、权限不足与身份解析失败。先定义可识别的可见范围并记录实测，后台标签存在不算可见。
- 回归：工作台和角色一致；新一轮仍能提醒；看见问题卡不会自动批准；历史不丢失、不重复写入；中文／英文均无“回复结束＝任务完成”的误导。

最低关闭条件：每项都有修复前样本、修复后自动检查，以及对应真实 Claude／Mac 安装包的独立环境证据。模拟事件或作者电脑上的成功，只作为其覆盖范围内的证据。
