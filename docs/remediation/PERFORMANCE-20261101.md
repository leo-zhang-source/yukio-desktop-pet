# 日志读取性能：事前标准与结果

2026-11-01。基础源码 `9227f812a552b83c1a257a8ef6bcd55b45395b4e`，Mac arm64，优化构建。使用人工日志，2 个 Codex 聊天、2 个 Claude 聊天，运行真实来源读取器；不读取私人聊天。主线程依次读取 Claude、Codex，与 App 的调用方式一致。每次运行使用新目录，6 次轮询；空闲、每轮每文件新增 10 条、一次每文件新增 1,000 条，各运行 3 遍。输入记录含时间、独立会话与调用编号。

修前突发负载共 4,000 事件，主线程单轮 1,394.9～1,417.2 ms；普通负载单轮 14.1～20.9 ms；空闲最大 0.28 ms。`AppController.tick()` 每 8 次绘制回调同步调用 `feeds.poll`，这些读盘和解析时间会占用界面线程。本测试是调用耗时证据，尚不能代替真实窗口输入延迟、磁盘争用或超大历史的验收。

## 实现前制定的验收线

- 固定三类输入各运行 3 遍；事件数量、身份及单会话顺序不能改变，不允许靠丢弃输入降低耗时。
- 普通负载每次轮询不超过 25 ms；突发负载每次轮询不超过 100 ms；空闲不超过 5 ms。同机比较，报告每遍与最长单次，不只报告平均值。
- 先去除已定位的重复解析器初始化；若仍超过上述标准，再单独移动一个来源的读取链路，增加代次、取消、退出与顺序检查。避免在尚可小范围修复时同时改写多个来源线程模型。
- 原有事件协议、时间格式、状态和取消规则保持不变；必须重跑共用样例和全部回归。

原始数值、修前失败和本轮全部证据保存在本机本轮备份目录；最终结果另补在本文件，不覆盖修前数据。

## 初步修后结果

保留 Foundation 旧解析器处理非标准 UTC 格式，标准零／三位小数 UTC 使用值类型 ISO8601 解析。单纯缓存旧解析器仍约 449 ms，未达到事前标准，未将该中间结果登记通过。

最终算法初测：空闲三遍最长 0.36／0.47／0.31 ms，普通负载 1.53／1.25／1.07 ms，突发 71.18／65.12／60.90 ms。每遍 4,000 条突发事件的身份与会话内顺序一致。时间解析的精度噪声与非法小时兼容差异在测试中暴露后已修正；失败日志保留。因局部优化已降至事前 100 ms 标准以下，本轮不引入线程重写；没有新增取消、退出或跨线程传递语义。

复现命令：`python3 scripts/run-source-benchmark.py --out <新目录>`。源码在 `tests/remediation/source-benchmark/main.swift`，只生成自己的 4 个测试聊天，独立目录运行，不访问真实账号或记录。最终提交、包和最后一次测试证据由阶段总记录补充。
