## 证据和修正

1. **模型回答结束被当作整个客户端任务结束。** 旧解析器把文本中的 `end_turn` / `stop_sequence` 立即转换为最终回答和任务结束。实际记录中，一条正常的 `end_turn` 后没有匹配的结束摘要，之后出现自动上下文、重试及继续调用工具。保留原生命周期结构、替换正文和标识后，安装版原生 CLI 回放先举牌，后续工作到达时又撤下；候选版不举牌。这个实际片段的后续助手活动间隔为 3598.589 秒，证明误判路径，但不能据此断言就是用户看到的那次短暂闪现。
2. **Stop 的后台信息被忽略。** 首次检查的三条 Stop 都包含运行中的后台任务；随后保存的元数据快照包含 14 条，均带 2–3 个后台任务。进一步按明确 prompt 身份及助手文本在本地匹配的 16 个 Stop 观察，也证实 `end_turn` 后仍可能有后台工作。这些记录没有发生时间戳；接收时间不能代替转录发生时间。[官方 Stop 说明](https://code.claude.com/docs/en/hooks#stop)也说明 hook 可使工作继续，后台任务与定时唤醒需要单独判断。快照采样时间不同，数量不作为唯一轮次数。
3. **旧事件可能污染新轮次或重新举牌。** 修前五项回归全部失败，共八处断言：短暂误举牌、混合工具/文本完成误判、未识别继续请求、旧回答附到新请求，以及已点掉的完成牌被同时间戳事件重新举起。

现在只在本轮非合成 `end_turn` 回答的 UUID 与 `stop_hook_summary.parentUuid` 精确匹配，且摘要明确没有阻止、输出、错误或继续上下文时发出一次完成事件。新请求、工具活动、已识别的主循环 API 请求和重试使旧回答失效；按明确 session/prompt 关联的后台任务或定时唤醒否决完成。单条 Stop 不再生成完成事件。未知字段或缺失确认不会猜测成功。

转录可读时，它负责活动顺序；hook 接收时间不再覆盖同一转录的轮次。读取 hook 时仍保留后台状态的补充作用，启动时只恢复有限的 Stop 元数据，不重播旧活动；跨启动的半条 JSON 在写完后仍可交付。转录不可读时保留 hook 活动回退。子代理、其他聊天、旧 prompt 与不同回答 UUID 不借用主任务身份。

路由器拒绝早于新请求或新活动的结束事件，同时间戳重复完成不能重新举牌；被拒绝的旧事件和仅标题更新不再充当活动心跳。收到继续思考后撤销尚未确认的最终回答。
